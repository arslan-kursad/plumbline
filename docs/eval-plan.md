# plumbline — Evaluation Plan (Pre-Registration)

**Version:** 0.1 · **Status:** DRAFT — NOT FROZEN · **Date:** 2026-08-19
**Work package:** F0 / W3 · **Repo target:** `docs/eval-plan.md`
**Semantic conventions:** OTel GenAI semconv pinned at v1.41 (upstream status:
**Development** — see SC-1)

> This document is a pre-registration. Once frozen (§2), every number, rule and
> procedure in it is a commitment made *before* the corresponding data is observed.
> Post-freeze changes require an ADR (§12). Analyses not registered here are labelled
> **exploratory** wherever they are reported.

---

## 1. Purpose

Make the four project success criteria falsifiable: for each, an exact metric, a
measurement method, a data source, a decision threshold, and a rule for what counts as
failure. Additionally, specify the seeded-regression controlled experiment, the
judge-tier agreement study, and the operating contract of the CI regression gate.

## 2. Freeze mechanics

A single freeze is not achievable: thresholds that discriminate signal from noise
require a baseline variance estimate, and no agent data exists at the F1 entry gate.
Pretending otherwise would produce arbitrary constants dressed as pre-registration.
Therefore the freeze is two-stage.

| Stage | When | What it fixes | What it may **not** do |
|---|---|---|---|
| **Freeze A** | F1 entry gate (human action) | Criteria, metrics, endpoints, statistical tests, decision rules, threshold *formulas*, rubric text, dataset spec & splits, degradation catalog, experiment design | — |
| **Freeze B** | F3, before the first seeded-regression run | Numeric constants derived **only** by applying Freeze-A formulas to the baseline calibration run (§7.3) | Add/remove endpoints, change tests or rules, alter the rubric, reweight metrics |

- Both stages are recorded as annotated git tags (`eval-plan-freeze-a`,
  `eval-plan-freeze-b`) plus the SHA-256 of this file at that commit.
- Every eval run records `plan_version` and `plan_sha256` in the Firestore `eval_runs`
  document (architecture §4.2). A run whose plan hash is absent is not admissible
  evidence for any criterion.
- Freeze B is mechanically constrained: the constants live in
  `docs/eval-plan.constants.yaml`, generated by `tools/calibrate.py` from the
  calibration run artefacts. A hand-edited constants file is a process violation.

## 3. Out of scope

- Implementation of checks, judges, harness or gate — owned by the F3 eval-engine spec.
- `eval_results` BigQuery schema — F3 (architecture §10 OQ-1). §9 states only the
  minimum fields this plan requires it to carry.
- Evaluating Claude Code as an agent. It is an *emitter* source for SC-1/SC-2 only; its
  behaviour is not controllable, so it cannot participate in a controlled experiment.
- Cost/performance benchmarking of the LLM providers themselves.

## 4. Context files

- `docs/architecture.md` v0.3 — §3.3 (dedup), §4.1 (`spans_deduped`, `spans_real`,

## 5. Measurement infrastructure

### 5.1 Units of evaluation

| Term | Definition |
|---|---|
| **Item** | One task instance from a frozen dataset (input + optional reference label). |
| **Run** | Execution of one agent variant over one dataset split, producing one trace per item. |
| **Trace** | The OTLP trace emitted by that execution, queried from `spans_deduped` / `spans_real`. |
| **Verdict** | Per-item, per-check result: `pass` / `fail` / `error`. `error` (harness or quota failure) is never silently coerced to `fail`; it is reported separately and excluded from the denominator only if `error_rate ≤ 2%`, otherwise the run is void. |

All evaluation reads BigQuery **views**, never the base table (architecture §4.1).
Evaluation of a run must be reproducible from the trace alone: if a metric cannot be
computed from persisted telemetry, it is not a valid metric here.

### 5.2 Datasets, splits, freezing

- One dataset per evaluated agent: `adjudicator-v1`, `triage-v1`.
- Split, assigned once by seeded hash of item id: **dev 30% / gate 70%**.
  - `dev` — used while authoring checks and rubrics. Freely inspectable.
  - `gate` — used only by gate runs and the seeded-regression experiment. Per-item
    outputs are not inspected while tuning checks.
- Frozen by checksum, referenced from Firestore `datasets` (architecture §4.2);
  immutable after freeze. Adding items creates a new dataset version, never mutates one.
- **Target size:** `N_gate ≥ 160` per agent (justification in §7.5). If the achievable N
  is smaller, the dataset is frozen at the achieved N and the **achieved MDE is recorded
  in the constants file and reported alongside every result**. Silently keeping the
  original δ at an underpowered N is forbidden.
- Human reference labels: a 50-item stratified subset of `gate`, labelled **before** any
  judge output is seen (§8.4).

### 5.3 Provenance pinning

Every run records: agent commit SHA, model id + version string, temperature and decoding
params, prompt template hash, dataset id + checksum, `plan_sha256`, harness version,
judge model ids + quantization, wall-clock window. Agent temperature is set to 0 where
the provider supports it; residual non-determinism is measured, not assumed away (§7.3).

## 6. Success criteria (measurable)

### SC-1 — Heterogeneous dialect normalization

**Claim:** ≥3 emitter dialects are normalized to semconv v1.41 without loss.

| # | Metric | Method | Data source | Threshold |
|---|---|---|---|---|
| 1.1 | Golden-file test pass rate | CI job, per dialect | `normalization/testdata/<dialect>/` | 100%, ≥3 dialects |
| 1.2 | Fixture provenance | Manifest per fixture records capture origin, emitter SDK + version, the semconv version **actually emitted**, the `OTEL_SEMCONV_STABILITY_OPT_IN` value (recorded as `unset` when absent) and the capture date | fixture manifest | ≥1 fixture per dialect **captured from a real emitter**, not hand-authored; a fixture missing any manifest field is not admissible evidence |
| 1.3 | **Losslessness** | Every attribute key in the input `ExportTraceServiceRequest` appears in a typed column or in the `attributes` JSON | normalizer output vs fixture | 100% of keys, all dialects |
| 1.4 | **Semconv conformance** | Every emitted `gen_ai.*` / normalized column name validated against a machine-readable copy of the pinned v1.41 registry vendored in-repo | `normalization/semconv/v1.41/` | 0 non-conforming names |
| 1.5 | Unknown-dialect fallback | Fixture with unregistered scope markers | golden test | `source_dialect='unknown'`, 0 dropped attributes, counter incremented |

1.3 and 1.4 exist because 1.1 alone is self-referential: the expected output is authored
by the same person as the mapping, so a passing golden test proves determinism, not
correctness. 1.3 and 1.4 are checks the author cannot satisfy by agreeing with himself.

**Stability of the pin.** At upstream tag `v1.41.0` the GenAI conventions carry status
**Development**: the document banner states it, and every `stability` field in
`model/gen-ai/registry.yaml` and `model/gen-ai/spans.yaml` reads `development` — none is
`stable`. The pin is therefore a contract this project holds itself to, not a guarantee
inherited from upstream, and claims made from SC-1 say so. Upstream additionally carries a
transition rule: an instrumentation already emitting the conventions of v1.36.0 or earlier
keeps emitting them by default, and the newer shapes are opt-in via the
`OTEL_SEMCONV_STABILITY_OPT_IN` environment variable. A fixture whose emitted convention
version and opt-in value are unknown cannot support the claim in this section, which is
what 1.2 records.

**Verdict rule:** SC-1 met iff all five rows pass in CI on `main`.

### SC-2 — 14-day continuous ingest from 3 real sources

Two distinct properties are conflated by the phrase "uninterrupted ingest" and are
separated here: an idle agent is not a pipeline failure.

| # | Metric | Method | Data source | Threshold |
|---|---|---|---|---|
| 2.1 (primary) | Real-traffic continuity | ≥1 span with `synthetic=false` per source per UTC day | `spans_real` grouped by `DATE(start_time)`, `source_dialect` | 14/14 days × 3 sources |
| 2.2 (diagnostic) | Pipeline availability | Heartbeat trace per dialect every 60 min, `synthetic=true` | `spans_deduped` | ≥99% of expected heartbeats present within 5 min of emit; no 2 consecutive misses |
| 2.3 | End-to-end loss | Load generator emits K spans with known ids; count distinct `(trace_id, span_id)` | `spans_deduped` | ≥99.9% delivered |
| 2.4 | Poison-message containment | DLQ depth alert (architecture §3.4) | `traces-dlq` monitoring | Any DLQ message triggers an incident note; unexplained DLQ ≠ pass |

Heartbeats are synthetic and therefore walled off (`synthetic=true`) — they are
diagnostic evidence, never counted toward 2.1. Their function is attribution: a 2.1
failure with 2.2 green is an idle agent; a 2.1 failure with 2.2 red is a pipeline defect.
Only the second is a platform failure, and the write-up must state which occurred.

**Verdict rule:** SC-2 met iff 2.1 holds for all three sources over one contiguous
14-day window, with 2.2–2.4 recorded for that window.

### SC-3 — Seeded regression caught by the gate

Full design in §7. Summary criterion:

| # | Condition | Threshold |
|---|---|---|
| 3.1 | Positive control (D6) | Gate fires, 5/5 runs |
| 3.2 | Primary degradation (D2) | Gate fires with pre-registered endpoints and thresholds |
| 3.3 | Negative control (baseline vs baseline) | Gate fires 0/5 runs |
| 3.4 | Threshold provenance | `plan_sha256` recorded before variant runs executed; thresholds not modified afterwards |

**Verdict rule:** SC-3 met iff 3.1, 3.2, 3.3, 3.4 all hold. If 3.2 fails while 3.1 and
3.3 hold, the result is reported as a **negative finding** — the gate is insufficiently
sensitive for quality-only regressions at N_gate — together with the achieved MDE. That
outcome is published, not suppressed (§11).

### SC-4 — Overhead, resource ceiling, cost

**4a — collector and agent overhead.**

With an async batch span processor, exporting does not sit on the agent's critical path;
the honest agent-side cost is CPU/RSS, not latency. Measured accordingly.

| # | Metric | Method | Threshold |
|---|---|---|---|
| 4.1 | Collector handler latency p95/p99 | In-process histogram under load profile L1 (Appendix A, P10), 10-min sustained | p95 ≤ `T_p95`; documented regardless |
| 4.2 | Collector RSS ceiling | Cloud Run container memory metric, p99 over the load window | ≤ 60% of the provisioned Cloud Run memory limit; 0 OOM restarts |
| 4.3 | Export rejection rate at max-instances=2 | Collector 429/5xx counter | ≤ 0.1% at L1 |
| 4.4 | Agent-side overhead | A/B: OTLP export enabled vs disabled, 3 runs each, same workload | Report median Δ RSS and Δ CPU with range; **documentation is the criterion**, no pass/fail threshold |

Load profile L1 parameters are constants set at Freeze B from the F2 capacity probe.
All load-generator traffic carries `synthetic=true`.

**4b — cost.**

| # | Metric | Method | Threshold |
|---|---|---|---|
| 4.5 | Monthly GCP bill | Billing console, archived screenshot per month | $0.00 for two consecutive calendar months |
| 4.6 | Daily spend | Daily check; any non-zero day → incident note in `docs/` (architecture §7) | 0 unexplained non-zero days |
| 4.7 | Kill-switch | F0 live-fire evidence + re-attach runbook | Present and dated |

**Verdict rule:** SC-4 met iff 4.1–4.3 pass their thresholds, 4.4 is documented, and
4.5–4.7 hold.

## 7. Seeded-regression controlled experiment

### 7.1 Subject

Primary subject: **Anomaly Adjudicator** (LangGraph/Python). Replication on **Apartment
Triage** (.NET) if budget allows; replication is a stretch goal and its absence is not a
criterion failure. Claude Code is excluded (not controllable).

### 7.2 Variants

Baseline `B0` is a pinned commit. Each degradation is a single-factor change from `B0`,
applied on its own branch, with no other diff.

| ID | Degradation | Expected detection route | Role |
|---|---|---|---|
| D1 | Agent model downgraded one class | Deterministic + judge | catalog |
| D2 | **Prompt ablation:** remove the constraint/rubric section of the system prompt | Judge tier primarily; output stays well-formed | **primary** |
| D3 | Few-shot examples removed | Judge tier | catalog |
| D4 | Evidence/context truncated to 1 item | Both | catalog |
| D5 | Tool errors caught and ignored | Behavioral invariants (R4) | catalog |
| D6 | `max_tokens` truncated below typical output length | Output-contract checks (R3) | **positive control** |
| — | `B0` re-run, no change | none should fire | **negative control** |

D2 is the primary case deliberately: it is the *hardest realistic* regression, because
the agent keeps producing structurally valid output and only quality degrades. A gate
that only catches D6 catches crashes, not regressions. D6 and the negative control bound
the experiment from both sides — without them, "the gate fired" is uninterpretable.

### 7.3 Baseline calibration (input to Freeze B)

- `k = 5` independent `B0` runs over the `gate` split, identical config, fresh processes.
- Yields baseline mean `μ0` and standard deviation `σ0` per endpoint. `σ0` is the
  residual non-determinism of the agent + judges; it is the noise floor the gate must
  clear.
- Constants written by `tools/calibrate.py`; no manual edits.

### 7.4 Endpoints, tests, and the decision rule

Pre-registered family of exactly **three** endpoints, in fixed order:

| Rank | Endpoint | Definition | Test |
|---|---|---|---|
| E1 (primary) | `task_pass_rate` | Fraction of items passing the composite deterministic contract R1∧R2∧R3∧R4 (§8.1) | McNemar exact, paired on item id, one-sided (variant worse) |
| E2 | `judge_mean_score` | Mean of the frozen rubric score across items (§8.2) | Wilcoxon signed-rank, paired, one-sided |
| E3 | `behavioral_budget_violation_rate` | Fraction of items exceeding pinned tool-call / token / latency budgets | McNemar exact, one-sided |

**Gate fires** iff, for at least one endpoint, **both** conditions hold:

1. **Statistical:** p < 0.05 after **Holm correction** across the family of 3.
2. **Practical:** the observed drop exceeds the pre-registered minimum effect —
   - `δ_min(E1) = max(0.05, 2·σ0(E1))`
   - `ε_min(E2) = max(0.25 rubric points, 2·σ0(E2))`
   - `δ_min(E3) = max(0.05, 2·σ0(E3))`

Requiring both prevents two distinct failure modes: firing on a statistically detectable
but operationally irrelevant drift, and firing on a large drop that is inside the agent's
own run-to-run noise. Paired tests are used because both arms run the same items; this is
materially more powerful than unpaired comparison at these sample sizes.

### 7.5 Power and MDE

Sizing assumption for `N_gate ≥ 160`: unpaired two-proportion, one-sided, α = 0.05,
power = 0.80, `p_baseline = 0.90`, `δ = 0.10` → n ≈ 157 per arm. Because the design is
paired, this is a **conservative upper bound**; the realized power depends on the
discordant-pair rate, which is unknown before calibration.

At Freeze B, `tools/mde.py` computes the achieved MDE per endpoint from the calibration
data and writes it into the constants file. Every reported result cites the achieved MDE.
A non-firing gate at an unreported MDE is not evidence of absence.

### 7.6 Blinding and audit

- Thresholds are computed from `B0` calibration only, never from variant runs.
- Freeze B tag exists in git **before** any variant run is executed; `eval_runs` stores
  `plan_sha256` per run and is the audit trail.
- Any threshold change after seeing variant results invalidates SC-3 and is reported as
  such. There is no path in which the experiment is quietly re-run with new thresholds.

## 8. Metrics and judges

### 8.1 Deterministic check families (R)

| ID | Family | Examples |
|---|---|---|
| R1 | Trace structural validity | root span present, ≥1 `gen_ai` operation span, no orphan spans, terminal `status_code` set |
| R2 | Telemetry schema conformance | required v1.41 attributes present for the operation type; names in registry |
| R3 | Output contract | output parses; required fields present; enum values in allowed set |
| R4 | Behavioral invariants | tool-call count within bounds; no identical tool call repeated > k times (loop detection); token and latency budgets |
| R5 | Task-specific rules | `P4` |

Exact rule bodies are F3 implementation; their **definitions and the composite contract
R1∧R2∧R3∧R4** are frozen at Freeze A.

### 8.2 Judge rubric

- Ordinal **4-point** scale, no neutral midpoint, with written anchors per point.
- Dimensions: **J1 groundedness** (does the stated rationale rest on evidence present in
  the trace inputs), **J2 instruction adherence** (against the pinned task contract).
  `judge_mean_score` = mean of J1 and J2.
- Rubric text is a frozen artefact (`docs/eval/rubric-v1.md`, hashed at Freeze A). A
  rubric edit is a measurement-instrument change and requires an ADR.
- Judges are given the task input and the agent output only — never the variant label,
  never the baseline output. Position/verbosity confounds are limited by a fixed
  presentation template.

### 8.3 Judge tiers and routing

| Tier | Model | Scope |
|---|---|---|
| T1 | Local Ollama, model id + quantization pinned | All items, 3 repeats each |
| T2 | Gemini Flash (AI Studio free tier), client-side rate limiter | Items where T1's 3 repeats are not unanimous, plus a seeded 20% random sample for drift monitoring, subject to daily quota cap `Q` |

- The **primary** gate endpoint (E1) is deterministic by design, so judge quota is never
  on the critical path of the gate.
- **Quota exhaustion is never a silent pass.** If T2 cannot complete its assigned set,
  the run is marked `judge_incomplete=true`, E2 returns `UNKNOWN`, and the gate decides
  on E1 and E3 only — with the incompleteness recorded in the run and surfaced in CI
  output. A run that reports a verdict without disclosing incompleteness is a defect.

### 8.4 Judge-tier agreement study

Agreement between two judges does not establish validity: both can agree and both be
wrong. The study therefore has a human anchor.

| Measure | Definition | Sample |
|---|---|---|
| A1 | Inter-tier agreement: Cohen's quadratic-weighted κ, T1 vs T2 | Full T2-judged set |
| A2 | Intra-judge self-consistency: % identical across 3 repeats, per tier | All items |
| A3 | Validity vs human: quadratic-weighted κ of each tier against the 50-item human reference subset | 50 items |
| A4 | Human intra-rater reliability: same labeller, two passes ≥7 days apart, blind to the first pass | 50 items |

**Pre-registered routing decision rule:** T1 is used for bulk judging iff
`A1 ≥ 0.60` **and** `A3(T1) ≥ A3(T2) − 0.10`. Otherwise T1 is demoted to a pre-filter
and T2 adjudicates every disagreement, subject to quota.

A4 bounds the ceiling of A3: no judge can be shown to exceed the reliability of the
reference labels themselves. With a single labeller, A4 is a known weakness (§10) and is
reported with the results, not omitted.

## 9. Gate operating modes

| Mode | Trigger | Scope | Authoritative for |
|---|---|---|---|
| PR | Pull request | Golden-file tests + deterministic checks on `dev` split; **no LLM calls**; target < 2 min | fast feedback only |
| Nightly | Cloud Scheduler | Full gate on `gate` split, tiered judges | SC-2, routine regression detection |
| Experiment | Manual, tagged | Baseline + variants per §7 | **SC-3** |

Minimum fields the F3 `eval_results` schema must carry for this plan to be enforceable:
`run_id`, `plan_version`, `plan_sha256`, `dataset_id`, `dataset_checksum`, `variant_id`,
`agent_commit`, `model_id`, `item_id`, `check_id`, `verdict`, `score`, `judge_tier`,
`judge_model_id`, `repeat_index`, `judge_incomplete`, `error_reason`, `run_ts`.
The rest of the schema is F3's to design.

## 10. Threats to validity (registered before results)

| # | Threat | Mitigation | Residual |
|---|---|---|---|
| V1 | Golden tests validate the mapping against its own author | SC-1 rows 1.3, 1.4 are author-independent | Fixture selection bias remains |
| V2 | Single labeller for the human reference set | A4 intra-rater reliability, blind second pass | No inter-rater reliability; ceiling on A3 |
| V3 | Judge self-preference / family bias (T2 judging output from a related model family) | Report the model families explicitly; human anchor A3 | Not eliminated |
| V4 | Small N, low power | Paired tests, MDE published with every result | Quality-only regressions may be genuinely undetectable |
| V5 | Overfitting checks to the evaluation set | dev/gate split; gate outputs not inspected during tuning | Enforcement is procedural, not mechanical, in a solo project |
| V6 | Synthetic vs real traffic distribution shift | `synthetic` flag; SC-2 primary uses `spans_real` only | Overhead numbers (SC-4a) come from synthetic load |
| V7 | Agent non-determinism mistaken for regression | k=5 calibration; 2σ0 practical-significance floor | Wide σ0 shrinks detectable effects |
| V8 | Degradations are unrealistically obvious | D2 chosen as a hard, structure-preserving case; D6 as control | The catalog is still author-designed |
| V9 | Duplicate spans inflating counts | All reads via `spans_deduped` (architecture §3.3) | Dedup key assumes `(trace_id, span_id)` uniqueness |

## 11. Claims and publication policy

- Only registered analyses are stated as results. Everything else is labelled exploratory.
- Negative and null results are published on the same terms as positive ones — including
  a gate that fails to catch D2, or a local judge that fails the routing rule.
- Every quantitative claim in the README, blog series and talks cites the run id, the
  dataset checksum and the plan hash that produced it.
- Cost claims are supported by billing evidence, not by architecture reasoning.

## 12. Change control after freeze

Any change to a frozen element — criterion, endpoint, test, threshold formula, rubric,
dataset composition, split assignment, degradation catalog — requires a new ADR that
states: what changed, why, what data had already been observed at the time of the
proposal, and which prior results are invalidated. Version increments; the superseded
version stays in git history. Results produced under a superseded version are never
silently re-labelled as current.

Freeze B is the sole exception, and only within the bounds of §2.
